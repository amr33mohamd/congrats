## Delivery Roadmap & Sub-Agent Work Breakdown

### 0. Reconciled Stack — Final Decisions (conflicts resolved)

The Backend report assumed **Vercel + Supabase**; the DevOps report argued for **Cloudflare + Neon** and flagged two real blockers. I resolve in favor of DevOps on hosting/storage, and keep Backend's data model and security design intact. Final, locked decisions:

| Decision point | Conflict | **Final call** | Rationale |
|---|---|---|---|
| **App host** | Vercel Hobby vs Cloudflare Pages/Workers | **Cloudflare Pages + Workers**, Next.js 15 App Router | Vercel Hobby is **non-commercial only** — this product takes InstaPay money, so Hobby is a license violation; Cloudflare has no such clause and zero-egress media. |
| **Runtime caveat** | Workers CPU cap (10–50ms) | Use Next-on-Cloudflare; keep API handlers thin. **Heavy/rare ops** (pg_dump, image transforms) run in cron Workers or on-upload, not in request path | Stays inside Workers limits. |
| **Database** | Supabase Postgres vs Neon | **Neon Postgres** (pooled URL for app, direct URL for migrations) | Neon branches-per-PR; avoids Supabase's 7-day auto-pause. Still Postgres, so Backend's schema is unchanged. |
| **ORM** | Prisma vs Drizzle | **Drizzle** | Lighter/faster cold starts on Workers edge runtime than Prisma; Backend's schema ports cleanly. |
| **Auth** | Supabase Auth vs Clerk vs Auth.js | **Auth.js (NextAuth) on Neon**, email magic-link + Google | $0, no MAU cap, lives in our own DB. We lose Supabase RLS, so **ownership/authorization moves into the data-access layer** (every query scoped by `user_id`; admin checks via `admin_users`). This is the one place we trade defense-in-depth for free-tier fit — mitigated by a single audited repository layer. |
| **File storage** | Supabase Storage vs R2 | **Cloudflare R2** (private buckets: `experience-media`, `payment-proofs`), signed-URL upload + signed-GET render | Zero egress is decisive for media-heavy mobile links. Keeps Backend's two-bucket + signed-URL design. |
| **Image optimization** | Cloudinary vs CF Images | **Cloudflare Images / Worker resize** on upload → AVIF/WebP, ≤1600px, strip EXIF | Cloudinary's 25-credit tier is too small for photo-heavy use. |
| **Email** | Resend vs Brevo | **Resend** (3k/mo), bilingual templates, fire-and-forget (never blocks state transitions) | Sufficient for receipts + unlock notices. |
| **i18n** | — | **next-intl**, `[locale]` routing, `defaultLocale: 'ar'` | Both design reports agree. |
| **Animation** | — | **Motion (core) + Lottie (vector FX) + canvas-confetti (bursts) + CSS (floor)**; GSAP lazy-loaded for paid "cinematic" templates only | Per Design EN; keeps default player light for low-end MENA phones. |
| **Slugs / unlock** | — | **nanoid 12–16 chars**; `is_published`/`is_unlocked` server-set **only** on admin approval | Per Backend + Payment; the slug is useless until approval. |
| **Money** | — | Integer **minor units (piastres)** + explicit `currency`, snapshotted on order | Per Payment + Backend. |
| **Observability** | — | **Sentry** (errors) + **Cloudflare Web Analytics** | Free, privacy-friendly. |
| **Keep-alive/cron** | — | **Cloudflare Cron Triggers** for DB ping, order-TTL expiry, nightly pg_dump→R2 | Free. |

**One-line stack:** *Next.js 15 on Cloudflare Pages/Workers → Drizzle → Neon Postgres → R2 + CF Images → Auth.js → Resend → Sentry + CF Analytics, all bilingual via next-intl.*

### 1. Language Scope Recommendation: **Bilingual from Day 1 — but staged**

**Recommendation: ship bilingual infrastructure from the start, with Arabic as the default locale, but limit MVP *template* depth to one native variant per template.**

Why not English-only first: the audience skews Egypt/MENA, Arabic is the *default* locale, and RTL is not a late-stage "translation layer" — it's load-bearing for layout, animation direction, and font selection. Retrofitting RTL after building LTR is far more expensive than building direction-agnostic from line one (logical CSS properties, `dir` on root, `start/end/symmetric` animation tokens). So **the chrome (UI, dashboard, admin, player engine) is bilingual on Day 1.**

The pragmatic cut: **each MVP template ships in its single most-natural native variant** (e.g. Eid → Arabic-native; the rest → both where the top emotional categories justify it), rather than forcing a polished AR *and* EN design for all of them at once. The engine renders either direction; we just don't pay for double the *design* work in MVP. Phase 2 backfills the sibling variants.

## Backend Architecture & Data Model

### 1. Recommended Tech Stack (opinionated)

Use **one full-stack framework + one Backend-as-a-Service** to stay on free tiers and avoid stitching together five vendors.

| Layer | Choice | Why |
|---|---|---|
| Framework | **Next.js 15+ (App Router)** deployed on **Vercel Hobby** | Single codebase for marketing site, dashboard, admin, public player, AND the API (Route Handlers / Server Actions). SSR for the public share link (SEO + WhatsApp/OG previews matter for a shareable link). Edge-rendered, mobile-fast. |
| DB + Auth + File Storage | **Supabase Free** (Postgres 500MB, Auth 50k MAU, 1GB Storage, 5GB egress) | One vendor gives Postgres + email/OAuth Auth + S3-style object storage with signed URLs + Row Level Security. The screenshot-upload requirement and the auth requirement are both covered without adding a service. |
| ORM | **Prisma** (or Drizzle) against Supabase Postgres | Typed schema, migrations, relations. Use Supabase only as a Postgres host + storage; do auth via Supabase Auth but model app data with Prisma. |
| Media optimization | **Cloudinary Free** (optional, for delivery transforms) OR Supabase Storage alone | Supabase Storage holds originals; Cloudinary's free tier is added later only if you need on-the-fly resize/format for recipient photos. Start with Supabase + `next/image`. |
| i18n | **next-intl** | First-class App Router + RTL support; set `dir="rtl"` per locale, ICU plurals for Arabic. |
| Slugs/short links | **nanoid** (12–16 url-safe chars) | Cryptographically random, unguessable, URL-safe, collision-proof at this scale — critical because the slug IS the access control for an unauthenticated recipient. |
| Background/admin email | Supabase + **Resend** free tier | Order-approved notifications. |

> Caveat worth flagging: Vercel Hobby has no built-in DB and Supabase free projects **auto-pause after 7 days of inactivity** — a cron ping (Vercel Cron, free) or simply real traffic keeps it warm. Render is a viable single-platform alternative if you prefer DB+app under one roof, at the cost of cold-start spin-ups.

Justification in one line: **Next.js owns rendering + API + the public player; Supabase owns Postgres + Auth + signed-URL file storage** — two free accounts, zero servers to manage, RLS gives defense-in-depth on the pay-to-unlock flow.

### 2. Data Model

Conventions: all tables have `id uuid pk default gen_random_uuid()`, `created_at`, `updated_at`. Money stored as integer **piastres/cents** (`amount_cents`) to avoid float bugs. JSON columns are `jsonb`.

```sql
-- ============ IDENTITY ============
users (
  id            uuid pk,            -- mirrors supabase auth.users.id
  email         text unique not null,
  display_name  text,
  locale        text default 'en',  -- 'en' | 'ar' (UI preference)
  avatar_url    text,
  is_blocked    boolean default false,
  created_at, updated_at
)

admin_users (                       -- elevated roles, separate from end users
  id        uuid pk,
  user_id   uuid fk -> users.id unique,
  role      text not null check (role in ('admin','reviewer','superadmin')),
  created_at
)

-- ============ TEMPLATE CATALOG ============
categories (
  id            uuid pk,
  slug          text unique,            -- 'anniversary','valentine','eid'...
  name_en       text not null,
  name_ar       text not null,
  icon          text,
  sort_order    int default 0,
  is_active     boolean default true
)

templates (
  id              uuid pk,
  category_id     uuid fk -> categories.id,
  slug            text unique,          -- 'anniversary-classic-ar'
  title_en        text,
  title_ar        text,
  locale          text not null check (locale in ('ar','en')), -- native design variant
  direction       text not null check (direction in ('rtl','ltr')), -- RTL flag
  is_paid         boolean default false,
  price_cents     int default 0,
  currency        text default 'EGP',
  thumbnail_url   text,
  preview_link    text,                 -- demo experience to show on marketing page
  definition      jsonb not null,       -- ordered step defs + animation params (see §3)
  status          text default 'draft' check (status in ('draft','published','archived')),
  created_by      uuid fk -> admin_users.id,
  created_at, updated_at
)

-- ============ USER-CREATED INSTANCES ============
experiences (                            -- a.k.a. projects
  id              uuid pk,
  user_id         uuid fk -> users.id,
  template_id     uuid fk -> templates.id,
  title           text,                  -- internal label "For Sara <3"
  recipient_name  text,                  -- default name token, overridable per step
  locale          text not null,         -- chosen render locale
  direction       text not null,         -- rtl/ltr at render time
  status          text default 'draft'
                   check (status in ('draft','awaiting_payment','locked','published')),
  is_unlocked     boolean default false, -- true only after payment approved (or free)
  created_at, updated_at
)

steps (                                  -- per-experience content, bound to a template step def
  id               uuid pk,
  experience_id    uuid fk -> experiences.id on delete cascade,
  template_step_id text not null,        -- references definition.steps[].id in template
  order_index      int not null,
  recipient_name   text,                 -- per-step override (optional)
  text_content     jsonb,                -- { "heading": "...", "body": "..." } filled by user
  animation_config jsonb,                -- overrides/locked params (duration, transition)
  created_at, updated_at,
  unique (experience_id, order_index)
)

media (                                  -- uploads (recipient photos + payment screenshots)
  id            uuid pk,
  user_id       uuid fk -> users.id,
  experience_id uuid fk -> experiences.id null,
  step_id       uuid fk -> steps.id null,
  kind          text check (kind in ('step_image','payment_screenshot','thumbnail')),
  storage_path  text not null,           -- supabase storage key, NOT public url
  bucket        text not null,           -- 'experience-media' | 'payment-proofs'
  mime_type     text,
  width int, height int, bytes int,
  created_at
)

-- ============ MANUAL PAYMENT ============
orders (
  id                 uuid pk,
  user_id            uuid fk -> users.id,
  experience_id      uuid fk -> experiences.id,
  template_id        uuid fk -> templates.id,
  amount_cents       int not null,
  currency           text default 'EGP',
  instapay_handle    text,               -- the number/handle shown to user at order time (snapshot)
  status             text not null default 'pending'
                      check (status in ('pending','submitted','approved','rejected','refunded')),
  payment_ref        text,               -- user-entered InstaPay reference/txn id
  screenshot_media_id uuid fk -> media.id null,
  reviewed_by        uuid fk -> admin_users.id null,
  reviewed_at        timestamptz null,
  reject_reason      text null,
  created_at, updated_at
)

-- ============ SHAREABLE LINK ============
share_links (
  id            uuid pk,
  experience_id uuid fk -> experiences.id unique,
  slug          text unique not null,    -- nanoid, the public token
  visibility    text default 'public' check (visibility in ('public','unlisted','disabled')),
  expires_at    timestamptz null,        -- null = never
  view_count    int default 0,
  last_viewed_at timestamptz null,
  is_active     boolean default true,    -- flips false if order refunded/abused
  created_at
)

-- ============ GOVERNANCE ============
audit_log (
  id          uuid pk,
  actor_id    uuid null,                 -- user or admin
  actor_type  text check (actor_type in ('user','admin','system')),
  action      text not null,             -- 'order.approve','link.disable','login'...
  entity_type text, entity_id uuid,
  metadata    jsonb,                     -- before/after, ip, ua
  ip          inet, user_agent text,
  created_at
)
```

**Relationships:** `users 1—N experiences`, `experiences 1—N steps`, `experiences 1—1 share_links`, `experiences 1—N orders` (usually 1, but rejects create retries), `templates 1—N experiences`, `categories 1—N templates`, `media N—1 experiences/steps`, `orders 1—1 media (screenshot)`, `audit_log` references any entity polymorphically.

**Status lifecycle (order):** `pending` (created when paid template chosen) → `submitted` (user uploaded screenshot + ref) → `approved` (sets `experiences.is_unlocked=true`, `share_links.is_active=true`) or `rejected` (with reason; user may submit again).

### 3. Template-as-Data → Generic Player

Principle: a **template is a schema** (ordered step definitions + animation params + which fields the user fills). An **experience is data** that binds user content to those slots. The player reads `template.definition` + the experience's `steps[]` and renders generically — it never hard-codes any occasion.

**Template definition (`templates.definition` jsonb):**

```json
{
  "version": 1,
  "locale": "ar",
  "direction": "rtl",
  "theme": {
    "palette": ["#FFD6E0", "#7A1E3A", "#FFFFFF"],
    "fontHeading": "Aref Ruqaa",
    "fontBody": "Cairo",
    "music": "tracks/oud-soft.mp3"
  },
  "steps": [
    {
      "id": "intro",
      "layout": "centered-photo",
      "transitionIn": { "type": "fadeZoom", "durationMs": 1200 },
      "transitionOut": { "type": "fade", "durationMs": 600 },
      "holdMs": 3500,
      "slots": {
        "heading": { "type": "text", "editable": true,
                     "maxLen": 40, "default_ar": "كل سنة وإنتي طيبة يا {recipient}" },
        "body":    { "type": "text", "editable": true, "maxLen": 140, "default_ar": "" },
        "image":   { "type": "image", "editable": true, "required": false,
                     "aspect": "3:4", "max": 1 }
      },
      "animations": { "heading": "typewriter", "image": "kenBurns" }
    },
    {
      "id": "memories",
      "layout": "photo-grid",
      "transitionIn": { "type": "slideUp", "durationMs": 800 },
      "holdMs": 5000,
      "slots": {
        "heading": { "type": "text", "editable": true, "maxLen": 30,
                     "default_ar": "ذكرياتنا" },
        "gallery": { "type": "image", "editable": true, "min": 2, "max": 6, "aspect": "1:1" }
      },
      "animations": { "gallery": "staggerReveal" }
    }
  ]
}
```

**Bound experience (what the player actually plays):**

```json
{
  "experienceId": "9f2c…",
  "templateId": "a11b…",
  "locale": "ar",
  "direction": "rtl",
  "recipientName": "سارة",
  "steps": [
    {
      "templateStepId": "intro",
      "orderIndex": 0,
      "text": { "heading": "كل سنة وإنتي طيبة يا سارة", "body": "بحبك من أول يوم" },
      "media": [{ "slot": "image", "url": "https://…/signed/intro.jpg" }],
      "animationConfig": {}          // empty = inherit template defaults
    },
    {
      "templateStepId": "memories",
      "orderIndex": 1,
      "text": { "heading": "ذكرياتنا" },
      "media": [
        { "slot": "gallery", "url": "https://…/g1.jpg" },
        { "slot": "gallery", "url": "https://…/g2.jpg" }
      ],
      "animationConfig": { "holdMs": 6000 }   // user/admin override allowed
    }
  ]
}
```

Render algorithm: `for each step → look up its template step def by templateStepId → merge animationConfig over defaults → substitute {recipient} tokens → render layout with slot values + transitions`. Adding a new occasion = inserting a new template row. **Zero player code changes.**

### 5. Auth, Uploads, Public Render (all free-tier)

**Auth — Supabase Auth (free):** Email-magic-link + Google OAuth (low friction on mobile, Egypt-friendly). Session is an httpOnly cookie read in Next middleware. `users` row is upserted from `auth.users` on first login. Roles live in `admin_users`; middleware gates `/admin/*` and admin route handlers by checking that table. **Postgres RLS** is the backstop: e.g. `experiences` readable only by `user_id = auth.uid()`; `media` in `payment-proofs` bucket has no public policy at all.

**Uploads — Supabase Storage signed-URL flow (free, 1GB):**
1. Client calls `POST /api/media/sign` → server checks user quota, mime allow-list (`image/jpeg|png|webp`), declared size cap (e.g. 5MB), then asks Supabase for a **signed upload URL** scoped to a per-user key path (`{userId}/{experienceId}/{nanoid}.jpg`).
2. Browser PUTs the file directly to storage (bytes never touch the Vercel function → stays within free function limits).
3. Client calls `POST /api/media/confirm` → server verifies the object exists, reads dimensions/bytes, writes the `media` row.
- Two buckets: **`experience-media`** (private; served to recipients via short-lived signed GET URLs) and **`payment-proofs`** (private; readable only by reviewers — never user-public).

**Public render flow (unauthenticated recipient by slug):**
1. Recipient opens `https://app/p/{slug}` on their phone.
2. SSR page calls `getShareLinkBySlug(slug)`. Gate checks in order: link `is_active` && `visibility != disabled` && (`expires_at` null or future) && `experience.is_unlocked = true`.
3. If gated-out → render a neutral "This link isn't available" page (no detail leakage). If a paid experience isn't yet approved, the slug returns the same neutral page — **the slug is useless until approval.**
4. On success: build the bound-experience JSON (§3), mint **short-lived signed URLs** (e.g. 1h) for each media object, atomically `view_count++` and set `last_viewed_at`.
5. Stream to the generic player (client component) which plays steps with animations. OG meta is rendered server-side so the WhatsApp/iMessage share card shows the recipient name + thumbnail.

### 6. Security & Integrity — manual-payment trust flow

- **No early access:** Unlock is a server-side boolean (`experiences.is_unlocked`) set **only** by the admin approve handler inside a transaction that also flips `share_links.is_active`. The public render checks `is_unlocked`, never client state. A guessed/leaked slug for an unpaid experience returns the neutral page.
- **Unguessable slugs:** nanoid 12–16 url-safe chars (~70–95 bits) → not enumerable; rejected/disabled links flip `is_active=false` rather than deleting (preserves audit + lets you reactivate).
- **Screenshot storage:** `payment-proofs` bucket is fully private with **no public read policy**; only reviewers fetch via short-lived signed URLs. Strip the URL from API responses to non-reviewers. Validate mime + size on `media/sign`; never trust client-declared type alone — re-check `mime_type`/bytes on confirm.
- **Amount/handle snapshotting:** `orders.amount_cents` and `instapay_handle` are copied at order creation, so later price/handle edits can't retroactively change what the user agreed to pay (and what the reviewer verifies against the screenshot).
- **Idempotent approval & double-spend guard:** approve/reject handlers are no-ops if `status != 'submitted'` (prevents double-unlock or re-approving a refunded order). All transitions write an `audit_log` row with actor, IP, UA, before/after.
- **Rate limiting / abuse:** throttle `media/sign` (e.g. 20/min/user) and order creation (e.g. 5 pending orders/user) to stop storage flooding; throttle public `/p/:slug` per-IP to blunt slug enumeration and inflate-view abuse. Cap experiences/media per free user.
- **Reviewer protections:** require a non-empty `payment_ref` and an attached screenshot before an order can reach `submitted`; surface the expected amount + handle beside the screenshot in the admin queue to reduce approval mistakes. Restrict approve/reject to `admin_users` with `role in ('reviewer','admin','superadmin')`.
- **Defense in depth:** RLS policies enforce ownership even if a route handler has a bug; `is_blocked` users are rejected at middleware and their active share links can be bulk-disabled. Tokenized media URLs expire (1h) so a copied link from devtools dies quickly.

### 1. Overall Design Language

#### 1.1 Design principles
1. **Celebratory but premium** — emotion comes from motion, light, and depth, not from clutter or cheap clip-art. Generous whitespace, one focal element per moment.
2. **Mobile-first, thumb-first** — every primary action sits in the bottom 40% of the screen (the "thumb zone"); links are opened on phones.
3. **Direction-agnostic** — all layout uses logical properties (`margin-inline`, `padding-block`, `inset-inline-start`) so the same components serve LTR and RTL.
4. **Quiet chrome, loud content** — UI chrome (controls, progress) is translucent and recedes; the recipient's name, photo, and message own the stage.
5. **Token-driven** — two-layer tokens (global primitives → semantic aliases) so themes (per-occasion accent, dark surfaces) swap without touching components.

Motion is the product, so this is the most important section.

- **Easing tokens** (per 2026 platform guidance — prefer expressive standard curves):
  ```

  --spring-soft     stiffness 220 damping 26    (Motion spring for cards/photos)
  --spring-bouncy   stiffness 320 damping 18    (confetti pop, badges)
  ```
- **Duration tokens:** `--dur-1:120ms (micro) · 2:200ms (UI) · 3:320ms (transitions) · 4:480ms (step change) · 5:700ms (hero reveal)`. Step-to-step transitions sit at 320–480ms.
- **Choreography:** stagger children 40–60ms; never animate more than ~3 properties at once; animate `transform`/`opacity` only (GPU-cheap) — never `width/top/left`.
- **Reduced motion:** `prefers-reduced-motion: reduce` → replace slides/parallax with cross-fades ≤200ms, kill particle systems and parallax, keep content fully legible. This is a hard requirement, not a nice-to-have.
- **Purpose:** every animation either (a) reveals content, (b) signals state, or (c) celebrates a milestone. No decorative motion that delays reading the message.

### 2. The Animation Engine

#### 2.1 Library decision

| Library | Bundle | Best at | Verdict here |
|---|---|---|---|
| **Motion** (ex-Framer Motion) | ~30–60 KB gz | React-native declarative transitions, `AnimatePresence` step swaps, layout animations, springs, gesture/drag | **Core engine** ✅ |
| **GSAP** | large (~1.8 MB full, tree-shake to ~78 KB) | bulletproof timelines, complex sequenced step choreography, text splitting | **Optional, lazy-loaded** for premium "cinematic" templates only |
| **Lottie** (`lottie-web`/`dotlottie`) | ~50 KB + JSON | designer-made After Effects vector animations (balloons, hearts, fireworks, Eid lanterns) | **Decorative assets** ✅ |
| **canvas-confetti** | ~6 KB | confetti/particle bursts, GPU canvas, runs off-thread-friendly | **Celebration layer** ✅ |
| **CSS / Tailwind transitions** | ~0 | hover, fades, simple reveals, reduced-motion fallbacks | **Baseline everywhere** ✅ |

**Recommended stack:** **Motion as the orchestration core**, **Lottie for vector flourishes**, **canvas-confetti for bursts**, **CSS for the floor**, and **GSAP lazy-loaded only for a small set of "cinematic" paid templates**. This keeps the default player light for low-end MENA devices while allowing premium spectacle when justified. Motion wins the default because it has the smallest bundle of the JS options, native React `AnimatePresence`/spring support, and a strong maintenance health score.

#### 2.2 How a step renders and transitions

Each experience is a JSON timeline. A step template = a composition of **slots** (name, body text, image(s), accent shape) + an **animation preset** (in/out transition + per-slot reveal + ambient effect).

```
ExperienceData
 ├─ meta { occasion, lang/dir, theme, music, recipientName }
 └─ steps[]
     ├─ templateId  (e.g. "letter-reveal", "photo-parallax", "countdown")
     ├─ slots { name, body, images[], cta? }
     ├─ animation { in:"slide-up", out:"fade", reveal:"stagger", ambient:"floating-hearts" }
     └─ duration  (autoplay ms) | advance:"tap"
```

The **Player** renders one step at a time inside `<AnimatePresence mode="wait">`. Step swap = exit anim of step N (`--ease-exit`, 320ms) overlapping entrance of step N+1 (`--ease-emphasized`, 480ms). Within a step, slots reveal with a 50ms stagger (name → body → image). Ambient effects (Lottie loop or particle field) live in a layer behind the content and persist across the step's lifetime.

#### 2.3 Autoplay vs tap-to-advance

- **Default: hybrid.** Each step autoplays its reveal, then waits. A subtle **timed ring** around the next-arrow fills over the step's `duration` (e.g. 5s) and auto-advances; **tap anywhere advances immediately**, **tap-left goes back** (like stories). The creator can set a step to `advance:"tap"` (manual only) for emotionally heavy moments (e.g. the proposal line) so it never rushes.
- Respect the scrollytelling lesson: never trap the user — a persistent **skip / progress dots** header lets them jump. Guided but escapable.

#### 2.4 Music / sound

- **Mute by default**, always (browser autoplay policy + the 2026 "User First" rule). A prominent **Unmute** pill appears on the first frame; one tap starts the soundtrack from the creator's chosen track.
- Track library (royalty-free, per occasion) + optional creator upload (admin-moderated). Ambient volume can duck on emotionally key steps.
- Haptic light-tap (`navigator.vibrate`) on confetti moments where supported.

#### 2.5 Confetti / particles

- `canvas-confetti` for bursts at the finale and milestone steps (hearts, stars, gold foil shapes, occasion-tinted). Origin can be from the CTA button or full-width cannon.
- Continuous ambient (floating hearts, falling petals, Eid lanterns, balloons) = a **single looping Lottie** or a lightweight CSS particle field — capped particle counts on mobile.

#### 2.6 Performance on low-end phones (hard constraints, free-tier + MENA)

- **Budget:** initial player JS ≤ ~120 KB gz; LCP < 2.5s; CLS ~0 (reserve image boxes).
- **Image pipeline:** auto-convert uploads to AVIF/WebP, responsive `srcset`, blur-up LQIP placeholder, served from a free CDN edge (e.g. Cloudflare/Netlify image). Hard cap upload size; client-side compress before upload.
- **Preload strategy:** preload step N+1's images during step N (idle-time `<link rel=preload>`); show a branded loader only if not ready.
- **Device tiering:** detect `navigator.hardwareConcurrency`/`deviceMemory` + Save-Data → "lite mode": fewer particles, cross-fades instead of parallax, no GSAP. Same content, lighter motion.
- **GPU discipline:** transform/opacity only; `will-change` toggled on just before a transition and removed after; passive touch listeners to avoid scroll jank; cap confetti particle count and stop the canvas on `visibilitychange:hidden`.
- **Fonts:** `font-display: swap`, subset to the languages/glyphs actually used.

## Arabic / RTL Design & Bilingual Strategy

This product is bilingual at its core: the UI, the marketing site, the dashboards, AND the celebratory templates all exist in two *natively designed* variants — Arabic (RTL) and English (LTR). The Arabic side is not a translation layer bolted onto an English design; it is a first-class design language. The guidance below is split into layout/mirroring, typography, implementation, cultural design, and structural divergence.

### 1. RTL Layout Strategy & Mirroring Rules

**Core principle:** drive everything off a single `dir` attribute on `<html>` (`dir="rtl"` for Arabic, `dir="ltr"` for English) and use **CSS logical properties** so one stylesheet serves both directions. Never hard-code physical sides (`left`/`right`, `margin-left`, `padding-right`, `text-align: left`). Use logical equivalents (`inline-start`/`inline-end`, `margin-inline-start`, `text-align: start`), which the browser maps to the correct physical edge based on `dir`. In Tailwind this means using `ps-*`/`pe-*`/`ms-*`/`me-*`/`start-*`/`end-*` instead of `pl/pr/ml/mr/left/right`, plus the `rtl:`/`ltr:` variants for the rare cases logical properties can't express.

**What MUST flip (mirror) in RTL:**
- **Whole-page layout & reading order** — page flows right-to-left. Sidebars, the dashboard nav, the primary content column, and the visual "first" item all move to the right.
- **Navigation, breadcrumbs, pagination, tabs, steppers** — order reverses; the "first / home / step 1" anchor sits on the right.
- **Text alignment** — Arabic body and headings align to the start (right edge).
- **Directional/navigational icons** — back/forward/next/previous arrows, carousel and slider controls, chevrons in menus, the "send" / submit arrow, expand/collapse carets that point sideways. In RTL "next/forward" points **left**, "back" points **right**.
- **Progress bars & step indicators in the experience builder** — fill grows from the **right**. The wizard "Step 1 → Step 5" advances right-to-left.
- **Sliders, range inputs, list bullets/numbering, drop-shadows implying a light source, and any "swipe to continue" affordance.**

**What must NOT flip (keep as-is in both directions):**
- **Logos and brand marks** (unless an official RTL lockup exists).
- **Media/playback controls** — play ▶, pause, fast-forward/rewind, and the **video/experience timeline scrubber stay LTR**. This is a hard, near-universal convention; mirroring the play button reads as "rewind/wrong." The congrats experience is essentially a media player, so the playback chrome stays LTR even in Arabic.
- **Clocks/time icons, circular refresh/spinner/loading indicators that imply clockwise motion** — do not mirror.
- **Numbers and Latin tokens** — phone numbers (the InstaPay number), the custom share-link URL, email addresses, prices, percentages, dates, and version strings stay LTR even when embedded in Arabic text.
- **Checkmarks, social-media glyphs, most non-directional icons** (camera, heart, gift, settings gear, image, trash).
- **Charts/graphs where the x-axis is inherently chronological LTR data** (admin analytics) — mirror with care or keep LTR.

**Animation direction — the load-bearing rule for storytelling:** Animation must follow reading direction, because animation *implies narrative progression*. In an **Arabic (RTL)** experience:
- Step-to-step transitions advance **right → left**. Content entering "from the future/next" slides **in from the left** and exits **to the right** (the opposite of the English build).
- Text reveals (typewriter, line-by-line, word-by-word stagger) start from the **right**.
- Parallax, "Ken Burns" pans, swipe-driven step changes, and confetti/streamer sweeps follow RTL flow.
- **Exception — symmetric/celebratory animations don't flip:** confetti bursts, fireworks, radial glows, scale-up "pop" reveals, balloon rises, sparkle scatters, and heart-float animations are direction-agnostic and should render identically in both. Only **directional/sequential** motion mirrors. Practically: store an animation's `direction` as a logical token (`start`/`end`/`symmetric`) in the template, not as `left`/`right`, and resolve it from locale at render.

### 2. Arabic Font Recommendations (specific Google Fonts)

**UI / system font (dashboard, marketing site, admin, forms, body):**
- **Cairo** — the safest all-purpose Arabic UI workhorse: clean, modern, excellent legibility across sizes and weights, pairs naturally with a Latin sans. Good default for the whole product chrome. *(Alt for a warmer, more "consumer/marketing" tone: **Tajawal** — slightly condensed, modern, great for headlines + body; or **Almarai** — friendly, very popular with Gulf/Saudi audiences and ideal for UI. For a corporate/admin feel: **IBM Plex Sans Arabic**, which has a true Latin sibling (IBM Plex Sans) for perfectly matched bilingual pairing.)*

Recommended **UI pairing:** Cairo (AR) + Inter or Plex Sans (EN), OR for a single typeface family that covers both scripts cleanly, **IBM Plex Sans Arabic + IBM Plex Sans**.

**Display / decorative fonts for celebratory templates (per occasion mood):**
| Font (Google Fonts) | Character | Best-fit occasions |
|---|---|---|
| **Aref Ruqaa** | Traditional Ruq'ah calligraphy, fluid upward slant, classic and warm | Wedding, Anniversary, Mother's/Father's Day, Thank You — classic & heartfelt |
| **Reem Kufi** | Modern geometric Kufic, bold and architectural | **Eid**, Ramadan, Graduation — festive, monumental headlines, ties into Islamic geometric motifs |
| **Lateef / Scheherazade New** | Naskh-rooted, ornate, literary, runs well at larger text lengths | Ramadan greetings with longer wishes, religious/formal congratulations |
| **Mirza** | Persian-influenced Nastaliq-flavored, elegant ornamental flow | Proposal, Valentine, Wedding — romantic, ornate, "invitation" feel |
| **Amiri** | Refined Naskh book typeface, dignified and elegant | Formal/religious occasions, Quranic phrases, classy wedding invites, condolence-adjacent "Get Well" warmth |
| **Lemonada / El Messiri** | Rounded, friendly, playful (Lemonada) / sturdy modern display (El Messiri) | **Birthday**, **Newborn baby**, Happy Eid (kids) — cheerful, soft |
| **Rakkas / Reem Kufi Ink** | Bold decorative display | High-impact festive hero titles |

**Usage rule:** Use **one display font for the recipient's name / step headline** and the **UI font (Cairo/Tajawal) for the longer custom message body** — display calligraphic faces (Aref Ruqaa, Mirza, Amiri) get hard to read in paragraph lengths. Per template, define a `displayFont` (headline) + `bodyFont` (message) pair rather than a single font.

### 3. Bilingual Implementation Strategy (Next.js / Tailwind)

**Stack:** Next.js App Router + **next-intl**. Routing via `[locale]` segment: `defineRouting({ locales: ['ar','en'], defaultLocale: 'ar', localePrefix: 'as-needed' })`. URLs become `/ar/...` and `/en/...`, which is also good for SEO and shareability.

**Direction & lang:** In the `[locale]/layout.tsx`, set `<html lang={locale} dir={locale === 'ar' ? 'rtl' : 'ltr'}>` via a small `getDirection(locale)` util (RTL set = ar, he, fa, ur). Because `dir` lives on the root, Tailwind's `rtl:`/`ltr:` variants and all logical properties resolve automatically with no per-component conditionals.

**Default & detection:** Audience skews Egypt/MENA, so **default to Arabic**. Detect via `Accept-Language` on first visit (middleware), but persist an explicit user choice in a cookie + on the user record so it survives across devices. A visible language toggle (showing "العربية / English") lives in the header and on the create flow; the public share link should encode the **experience's own** locale (the sender chose it), independent of the viewer's UI preference — the recipient sees the experience in the language it was authored in.

**Fonts loading per locale:** Load via `next/font/google` and scope by locale to avoid shipping Arabic glyphs to English users and vice versa. Apply the active font through a CSS variable on `<body>` (`--font-ui`), and load **display fonts on demand per template** (only fetch Mirza/Aref Ruqaa when a template that uses them renders) to keep within free-tier bandwidth and mobile performance. Use `display: 'swap'` and subset properly (`arabic` subset for AR faces).

**Content storage for both languages:** Store all translatable content as keyed objects, not flat strings:
- **UI strings** → next-intl message JSON files (`messages/ar.json`, `messages/en.json`).
- **Templates, categories, pricing labels** (admin-managed) → DB rows with localized fields, e.g. `title: { ar, en }`, `description: { ar, en }`, plus separate **`variant`** records since the AR and EN template designs differ structurally (see §5) — model them as two design variants under one logical template, each with its own font pair, ornament set, and animation direction tokens, rather than one design with swapped text.
- **User-authored content** (recipient name, per-step custom text) → stored once in whatever language the sender typed; mark each experience with an authored `contentLocale` that drives `dir` and font selection at playback.

**Mixed-direction (bidi) handling — critical for user-generated text:** Recipients' names, the InstaPay number, URLs, prices, and any Latin/numeric token inside Arabic text must be isolated so they don't scramble surrounding text:
- Wrap unknown-direction user input (names, especially) in `<bdi>` or apply `unicode-bidi: isolate`. Modern `dir="auto"` / the HTML default already maps to `unicode-bidi: isolate` (preferred over the older `embed`), which is far more predictable.
- For inputs, set `dir="auto"` so a field auto-aligns to the script the user types (an English name in an Arabic experience aligns LTR automatically).
- Numbers: decide **Western (1234) vs Eastern Arabic (١٢٣٤)** numerals deliberately. Egypt commonly reads Western Arabic numerals fine; use `Intl.NumberFormat` with the locale and a configurable numbering system. **Keep the InstaPay number, phone numbers, and the share URL in Western/Latin digits and LTR** regardless of locale to avoid copy/paste and dialing errors.

### 4. Cultural Design Guidance per Occasion (Arabic templates)

General tone: Arabic celebratory design leans toward **warmth, generosity, ornamentation, and rich jewel tones with metallic accents** (gold, brass, copper) far more than minimalist Western greeting design. Empty space is less prized; tasteful ornament reads as "premium/heartfelt," not cluttered.

- **Eid (Fitr & Adha) / Happy Eid:** Crescent moon + star, **fanous** (lanterns), mosque silhouettes, geometric Islamic star patterns (girih), arabesque cutwork. Palette: emerald/deep green, gold, deep blue/teal, with warm lantern glow. Use **Reem Kufi** for "عيد مبارك". Tone celebratory but with dignity. *Distinguish Eid al-Fitr (joyful, sweets, family) from Eid al-Adha — avoid sacrificial imagery; keep it festive/generic.*
- **Ramadan:** Crescent + lanterns + stars, soft night-sky tones, hanging ornaments, geometric patterns. Palette: midnight/royal blue, purple/amethyst, gold accents. Tone is **spiritual and serene**, warmer/quieter than Eid's burst. Common phrase "رمضان كريم". Honor the diversity of Muslim cultures (Moroccan, Turkish, Gulf, Egyptian motifs) rather than one stereotype.
- **Wedding:** Ornate arabesque borders, gold foil, florals, elegant calligraphic name treatment. Palette: ivory/cream + gold, blush, deep red, or emerald. Use **Aref Ruqaa / Amiri / Mirza** for the couple's names. Tone: formal, luxurious, "invitation-grade."
- **Anniversary / Valentine / Proposal:** Romantic florals, gold linework, soft glows, hearts (symmetric float animations). Palette: rose/burgundy, blush, gold. **Mirza** or **Aref Ruqaa** for names. Keep imagery **modest and tasteful** — overtly sensual visuals are culturally inappropriate for much of the MENA audience; lean romantic-elegant, not provocative.
- **Newborn baby:** Soft pastels (but in MENA, **richer pastels + gold** rather than washed-out Western pastels), crescents, little stars, gentle florals. **Lemonada/El Messiri** for a soft, friendly name display. Optional culturally common phrasings ("مبروك المولود"). Be neutral on gender unless the sender specifies.

**Sensitivities to avoid across all Arabic templates:**
- Do not place Quranic verses or sacred phrases casually in decorative/animated chrome; if used, treat with respect (Amiri/Naskh, no distortion, no playful motion).
- Avoid alcohol, pork, gambling, and immodest imagery in stock assets.
- Avoid imagery that conflates "Arabic" with only Gulf aesthetics — Egypt/Levant/North Africa have distinct visual traditions.
- Don't mirror or stretch calligraphy/sacred text; never apply RTL flipping to Arabic *script* itself (only layout flips, text shaping is handled by the font).

### 5. How Arabic vs English Templates Differ (natively designed, not translated)

The two variants share a **logical structure** (same step count, same data slots: name / text / images / animation) but diverge in design execution:

- **Typography weight & rhythm:** Arabic display faces (Aref Ruqaa, Mirza, Amiri) carry more **stroke contrast and ornament**, sit on a different baseline, and need **more line-height/leading** and larger sizes to render legibly than the Latin equivalent. The EN variant uses a Latin display font (e.g. Playfair Display for elegance, Poppins for fun) at tighter leading. Don't reuse the same point size — Arabic generally needs to be set larger.
- **Ornamentation:** Arabic variants justify **more decorative framing** — arabesque borders, geometric girih patterns, gold filigree — as a native aesthetic. English variants of the same occasion typically run **cleaner/more minimal**, with whitespace doing the work. Eid/Ramadan ornament (lanterns, crescents, Islamic geometry) is core to the AR variant and largely absent or restrained in the EN one.
- **Direction of motion:** All sequential/narrative animation mirrors (entrances from the left, reveals starting right, RTL step progression) as detailed in §1; symmetric celebratory effects stay identical.
- **Imagery & composition:** Photo crops, text-over-image placement, and the visual entry point shift to the **right** in AR. Cultural imagery differs (lanterns/crescents/arabesque for AR Eid vs. generic festive for EN). Modesty norms apply more strictly to the AR romantic templates.
- **Tone of copy & default phrasing:** Default placeholder text and suggested phrases are **idiomatic, not literal** ("عيد مبارك", "مبروك المولود", "كل سنة وانت طيب") — authored by an Arabic copywriter, not machine-translated from English.

**Implementation takeaway:** model each template as one logical template with two `variant` records (`ar`, `en`), each carrying its own `{ displayFont, bodyFont, ornamentSet, palette, animationDirection (start|end|symmetric per step), imageCrops }`. The builder picks the variant matching the sender's chosen language; the playback engine resolves direction and fonts from the experience's `contentLocale`.

## Template Catalog & Step/Animation System

This is the creative core of the product: a composable system where a small set of reusable **Scene types** + an **Animation preset library** combine into named **Templates**, organized under **Occasion categories**, and shipped in two native language variants (Arabic-RTL and English-LTR). The sender fills editable fields; the recipient opens a link on their phone and watches an auto-advancing (with tap-to-skip and tap-to-replay) animated story — a "mini movie trailer" feeling that 2026 ecard/invite trends are pushing hard (animated video invites, scrollytelling, AR/QR unlocks, AI personalization, lilac/warm palettes, handwritten script accents).

---

### 1. The Template System — Building Blocks

A **Template** = ordered array of **Scenes**. Each Scene = `{ sceneType, animationPreset(s), layout, fields[], theme tokens, timing }`. Themes are token-driven (color, font, motion-intensity) so the same Scene renders Arabic-native or English-native by swapping a theme + direction flag.

#### A. Scene "Scene" Types (the reusable structural blocks)

| Scene type | What it does | Core editable slots |
|---|---|---|
| **Cover / Intro** | Opening title card; sets the mood, names the recipient. Often a tap-to-begin ("Open your gift" / «افتح هديتك»). | recipientName, headline, sub-line, bg media |
| **Text Reveal** | A heartfelt message delivered as animated text (the emotional beats). | paragraph(s), optional signature |
| **Photo Reveal** | A single hero photo dramatically unveiled. | 1 image, caption |
| **Gallery / Memory Wall** | 3–12 photos in a moving collage or carousel. | image set, per-photo captions |
| **Countdown / Timeline** | Counts toward a date, or walks a relationship/life timeline ("2019 → today"). | date(s), milestone list, labels |
| **Quiz / Interaction** | A tap-to-answer or tap-to-continue moment ("How long have we…?", "Tap the heart"). | question, options, reactions |
| **Gift Reveal** | The "unwrap" beat — a box/envelope/lantern opens to reveal a message, code, or photo. | hidden payload (text/image/voucher) |
| **Map / Details** | For invites: venue map, date, RSVP/add-to-calendar, directions (QR-friendly). | location, datetime, RSVP link |
| **Audio Note** | Plays an uploaded voice message or chosen track over a still. | audio file, visual |
| **Finale / Confetti** | The payoff: confetti/particles/fireworks + final line + share/replay CTA. | closing line, signature, CTA |

#### B. Animation Preset Library (motion applied to any Scene)

Built on Lottie/CSS/Framer-Motion primitives; each preset has `intensity` (subtle/normal/cinematic) and respects `prefers-reduced-motion`.

- **Entrance:** Fade-up, Soft Zoom, Curtain Wipe, Letterbox Reveal, Iris/Spotlight open.
- **Text:** Typewriter, Word-by-word fade, Calligraphy draw-on (SVG stroke — essential for Arabic display scripts), Kinetic typography (bouncing/scaling words), Handwriting script trace.
- **Photo:** Ken Burns parallax, Photo Morph (cross-dissolve between two images), Polaroid drop-in, Shatter-to-reveal, Tilt/3D-card hover, Frame-fill (photo grows to fill).
- **Transition:** Slide, 3D Flip, Page-turn, Liquid/blob morph, Light-leak swipe.
- **Particle / FX:** Confetti burst, Heart-rain, Petal fall, Firework finale, Sparkle/bokeh drift, Falling stars, Bubbles, Snow/glitter.
- **Themed FX (occasion-specific):** Crescent-rise + lantern glow (Eid/Ramadan), Ring-sparkle (Proposal/Wedding), Balloon float + candle (Birthday), Cap-toss (Graduation), Footprint/stork trail (Newborn).
- **Ambient:** looping gradient mesh (lilac/warm 2026 palettes), grain, parallax depth on device tilt.

#### C. How they compose

A template author (admin) picks a category → drags Scenes into order → assigns each Scene a layout + 1–3 animation presets + theme tokens → marks which fields are **sender-editable** vs **locked design**. Output is a JSON template doc:

```
Template "Our Story" → [Cover(IrisOpen), Timeline(KenBurns+Typewriter),
  Gallery(PhotoMorph), Text(WordFade), GiftReveal(EnvelopeFlip),
  Finale(HeartRain+Confetti)]
```

The runtime player reads the doc, injects the sender's field values, and plays the sequence. Reusability: the same `Photo Reveal + PhotoMorph` block appears in Anniversary, Wedding, and Newborn templates with different themes — build once, reskin infinitely.

### 5. Maintaining Variety & Quality

- **Admin-authored only (curated):** All templates are created in the admin panel using the Scene + Animation composer — no end-user template editing. This guarantees motion polish and on-brand quality. End users only fill fields.
- **Versioning:** Each template doc has `version` + `status` (draft → review → published → archived). Editing a published template creates a new version; **already-sent links pin to the version they were created with** so a recipient's experience never breaks. Admin can A/B two versions and promote the winner.
- **Theme/variant integrity:** AR and EN variants are linked siblings of one logical template; QA checklist enforces correct direction, font fallback, calligraphy stroke rendering, and that no text overflows on a 360px-wide phone.
- **Free vs Paid tiers:**
  - **Free:** simpler templates (fewer scenes, lighter FX, basic fonts) — drives acquisition and link-sharing virality (every shared link is an ad).
  - **Paid:** "cinematic" templates (more scenes, premium animations like ring-sparkle/3D gift reveal, custom audio, calligraphy hero, more photo slots). Paid is enforced at link-unlock: user builds freely, but the link stays locked until the InstaPay screenshot is admin-approved.
  - Admin sets `tier`, `price`, and `featured`/`seasonal` flags per template (e.g. surface Eid/Ramadan templates seasonally on the marketing site and dashboard).
- **Freshness cadence:** ship 2–4 new templates each season (Ramadan/Eid, Valentine's, graduation season, wedding season), retiring underperformers to archive — keeps the catalog feeling alive and gives returning users a reason to come back.
- **Reuse leverage:** because Scenes + animation presets are shared primitives, a "new" template is mostly a new ordering + theme, so a designer can ship a fresh, desirable template in hours rather than building motion from scratch.

## Manual Payment, Orders & Admin Approval Flow

This flow is built around Egypt's **InstaPay** (the Central Bank of Egypt's instant payment app — money is sent 24/7 to a **mobile number / IPA**, and the sender gets a transaction confirmation with a reference number). Because there is no automated payment gateway, every paid order goes through a **screenshot-based, human-reviewed approval** before the share link unlocks. The design below assumes free-tier constraints (Supabase/Postgres + Storage, Vercel/Netlify functions, a free email tier).

---

### 1. Order Lifecycle — State Machine

An **Order** is the payment+fulfillment record attached to one **Experience** (the animated story). The Experience itself can be drafted/edited freely; it is the *publish/unlock* that is gated by the Order.

**States**

| State | Meaning |
|---|---|
| `DRAFT` | Experience being built; no payment intent yet. |
| `AWAITING_PAYMENT` | User chose a paid template/plan, checkout shown with InstaPay number + amount. No proof yet. |
| `PROOF_SUBMITTED` | User uploaded screenshot + reference + claimed amount. Enters admin queue. |
| `UNDER_REVIEW` | An admin has opened/claimed the order (soft-lock to avoid double-handling). |
| `APPROVED` | Admin verified payment. Link unlocks. Terminal-success. |
| `REJECTED` | Admin rejected with a reason. User can resubmit → back to `AWAITING_PAYMENT`. |
| `EXPIRED` | `AWAITING_PAYMENT` with no proof past TTL (e.g. 7 days). Reopenable. |
| `REFUND_REQUESTED` | Post-approval dispute opened by user. |
| `REFUNDED` | Admin marked refund done (manual InstaPay reversal); link re-locks. |
| `CANCELLED` | User abandoned before approval, or admin voided a fraudulent order. |

**Transitions (trigger → from → to)**

```
User: select paid template      DRAFT             -> AWAITING_PAYMENT
User: upload proof              AWAITING_PAYMENT   -> PROOF_SUBMITTED
System: TTL elapsed, no proof   AWAITING_PAYMENT   -> EXPIRED
User: reopen expired order      EXPIRED            -> AWAITING_PAYMENT
Admin: open/claim               PROOF_SUBMITTED    -> UNDER_REVIEW
Admin: approve                  UNDER_REVIEW       -> APPROVED        (unlocks link, sends "approved")
Admin: reject(reason)           UNDER_REVIEW       -> REJECTED        (sends "rejected" + reason)
User: resubmit new proof        REJECTED           -> AWAITING_PAYMENT (then PROOF_SUBMITTED)
User: cancel                    AWAITING_PAYMENT/REJECTED -> CANCELLED
User: request refund            APPROVED           -> REFUND_REQUESTED
Admin: process refund           REFUND_REQUESTED   -> REFUNDED        (re-locks link)
Admin: deny refund              REFUND_REQUESTED   -> APPROVED
Admin: void fraud               UNDER_REVIEW/APPROVED -> CANCELLED    (re-locks link)
```

**Enforcement rule:** transitions are executed by a single `transition_order(order_id, action, actor, meta)` server function (Postgres RPC / Edge Function). It validates the source state, writes the new state, **and** appends an audit row in the same DB transaction. The client never sets `status` directly; row-level security forbids it. `APPROVED` is the *only* state that flips `experiences.is_published = true`.

### 2. User-Facing Screens

**A. Checkout / "Pay with InstaPay" screen** (entered from `AWAITING_PAYMENT`)

Mobile-first, bilingual (RTL/LTR auto-switch). Shows:
- Order summary: template name + occasion, language variant, thumbnail.
- **Amount due** in large type: `350 EGP` (locked at order creation — see §4).
- A unique **Order Reference** the user must put in the InstaPay transfer note, e.g. `CG-7F3A9K` — short, uppercase, no ambiguous chars (no 0/O/1/I).
- **InstaPay recipient:** the platform's mobile number / IPA, with a one-tap **Copy** button (critical on mobile). Optionally a `tel:`-free deep link / QR.
- Step-by-step instructions (numbered, both languages): open InstaPay → send to *this number* → enter exactly *this amount* → put *CG-7F3A9K* in the note → screenshot the success screen.
- A countdown / "this quote is held until {date}" note tied to the TTL.

**B. Upload-proof form** (same screen, below instructions)
- File picker (image, also accepts PDF) — client compresses to <2MB, validates type. Live preview.
- **Reference number** field (the InstaPay transaction reference shown on their success screen).
- **Amount paid** field (prefilled with amount due; editable so admin can catch under/overpayment).
- Optional sender name / phone (helps matching).
- Submit → order → `PROOF_SUBMITTED`.

**C. "Awaiting approval" state** (after submit, `PROOF_SUBMITTED` / `UNDER_REVIEW`)
- Clear status banner: "Payment received — under review. Usually approved within X hours." Shows submitted screenshot thumbnail, reference, amount, and timestamp.
- The share link is shown **locked** (blurred preview, disabled copy button) with a lock badge.
- "Edit / replace screenshot" allowed only while still `PROOF_SUBMITTED` (not after `UNDER_REVIEW`).
- The user can keep editing the *content* of the experience while waiting (animations, text) — only publishing is gated.

**D. On `APPROVED`** — what unlocks:
- `experiences.is_published = true`; the **share link becomes live and publicly openable** (the recipient route returns 200).
- The dashboard reveals the full link with **Copy / WhatsApp / QR** share actions and a "Preview as recipient" button.
- Success toast + email/in-app notification.

**E. On `REJECTED`** — banner with the admin's reason (e.g. "Amount doesn't match", "Screenshot unclear", "Reference not found"), a "Pay again / re-upload" CTA returning to screen A. Previous attempt is preserved in history.

### 3. Admin Approval Queue

**Queue list view** — default filter `PROOF_SUBMITTED + UNDER_REVIEW`, sorted oldest-first. Per-row fields:
- Order ref (`CG-7F3A9K`), created time / age (SLA highlight if old).
- User (name/email), experience title + occasion + language variant.
- Expected amount vs **claimed amount** (mismatch flagged red).
- Claimed reference number.
- Status badge + which admin (if any) has it open.
- **Risk flags** (auto-computed): duplicate-screenshot-hash, duplicate-reference, amount mismatch, new account, many recent rejections.

**Detail / review panel:**
- **Screenshot viewer:** full-size with zoom/pan (to read amount/reference/date), rotate, and "open original". Side-by-side: image on one side, expected-vs-claimed amount + reference on the other.
- **Manual amount verification checklist** the admin ticks: amount matches, reference present in note, date is recent/plausible, recipient number correct. Approve is enabled only when the admin confirms (or explicitly overrides with a note).
- **Actions:** `Claim` (→ `UNDER_REVIEW`, soft-lock), `Approve`, `Reject` (requires choosing a reason from a fixed list + optional free text), `Void as fraud`, `Refund`.
- **Cross-reference:** clicking the reference/hash shows other orders sharing it.

**Audit trail** — every action writes an immutable `order_events` row: `{order_id, from_state, to_state, action, actor_admin_id, reason, claimed_amount, ip, created_at}`. Displayed as a timeline on the order. Admins cannot edit/delete events (append-only; enforced by RLS + no UPDATE/DELETE grant).

**Duplicate / fraud handling:**
- On upload, compute a **perceptual + SHA-256 hash** of the image; store it. If the hash already exists on another order → auto-flag "reused screenshot."
- Unique constraint attempt on (normalized reference number) → flag if a reference was already used to approve another order.
- Velocity flags: same user/IP submitting many orders; account age.
- Flagged orders are not auto-rejected — they surface to admin with the reason for a human decision.

### 4. Pricing Model & Storage

Support all three with one schema so product can choose later:
- **Per-template price** — each template has a base price.
- **Per-experience price** — resolved = template price (± modifiers like extra steps/images).
- **Credits / bundles** — user buys N credits via the same InstaPay flow; publishing an experience spends 1 credit (no per-order approval after the credit purchase is approved once).

**Schema (illustrative):**
```
products(id, type['template'|'plan'|'credit_bundle'], name_en, name_ar)
prices(id, product_id, amount_minor INT, currency='EGP', active BOOL, valid_from, valid_to)
   -- amount_minor = piastres (35000 = 350.00 EGP); integer, never float
orders(id, ref, user_id, experience_id, product_id, price_id,
       amount_due_minor, currency, claimed_amount_minor, coupon_id,
       status, screenshot_path, screenshot_sha256, reference_no, created_at)
coupons(id, code, type['percent'|'fixed'], value, currency, max_uses, used_count,
        valid_from, valid_to, min_amount_minor, active)
credit_wallets(user_id, balance)
order_events(...)  -- audit, append-only
```
Key rules:
- **Store money as integer minor units (piastres) + an explicit `currency`** column; never floats. Default `EGP`.
- **Snapshot** `amount_due_minor` onto the order at creation so later price/coupon changes don't alter an in-flight order.
- **Coupons:** validated server-side at checkout (active, in-window, under max-uses, meets min amount); discount applied to compute `amount_due_minor`; `coupon_id` stored on the order; `used_count` incremented only on `APPROVED` (so abandoned orders don't burn coupon stock).

### 5. Notifications (free-tier only)

- **In-app is the source of truth** (works with zero external cost): a `notifications` table + a badge/toast in the dashboard, updated live via Supabase Realtime. Triggered on every status change.
- **Email via a free tier** (e.g. Resend free, Brevo/SendinBlue free ~300/day, or SMTP) sent from the `transition_order` server function:
  - `PROOF_SUBMITTED` → "We received your payment proof — under review."
  - `APPROVED` → "Your gift is ready!" + the live share link.
  - `REJECTED` → reason + "re-upload" link.
  - Optional admin alert email on each new `PROOF_SUBMITTED`.
- Templates are **bilingual**, chosen by the user's locale.
- Send asynchronously / fire-and-forget with retry; a failed email must **not** block the state transition (in-app already covers it). No SMS (cost + deliverability); WhatsApp share is user-initiated, not a notification channel.

---

### 6. Data Integrity & Anti-Abuse

**Link cannot be accessed until approved** — defense in depth, not just UI:
1. The public recipient route resolves the share token **server-side** and returns 404/"locked" unless `experiences.is_published = true`, which is set **only** by the `APPROVED` transition.
2. **Row-Level Security:** the public/anon role can `SELECT` a published experience only; `is_published` is never client-writable. The share token is a long random unguessable slug (not a sequential ID), and the locked experience's content is not served at all (so it can't be scraped pre-approval).
3. Publishing flips back to locked on `REFUNDED` / fraud-`CANCELLED`.

**Preventing screenshot reuse:**
- `screenshot_sha256` (+ perceptual hash) stored and indexed; duplicate hash across orders is flagged and blocks silent auto-approval.
- Reference number normalized + uniqueness-checked against previously **approved** orders.
- Screenshots stored in a **private** Storage bucket; admins view via short-lived signed URLs (no public exposure of payment proofs / PII).

**Basic anti-abuse:**
- One active `AWAITING_PAYMENT`/`PROOF_SUBMITTED` order per experience (DB partial unique index) — no spamming the queue.
- Rate-limit proof uploads per user/IP; max file size + MIME validation server-side.
- Account-age and velocity flags surfaced to admins.
- All money math and all state transitions are **server-authoritative**; the client only requests actions.
- Idempotent approval: approving an already-`APPROVED` order is a no-op (guards against double-clicks / double-handling by two admins, backed by the soft-lock).

### 3. Environments, CI/CD, Secrets

- **Environments:** three logical envs.
  - `preview` — every PR auto-deploys a Cloudflare Pages preview URL; points at a **Neon branch** (instant copy-on-write DB per PR) and an R2 `dev/` prefix bucket.
  - `staging` (optional, `main` branch) — production-like, separate Neon branch.
  - `production` — protected branch (`release`/tag), production Neon branch, production R2 bucket, real Resend domain.
- **CI/CD (GitHub):**
  - GitHub repo → Cloudflare Pages Git integration auto-builds on push/PR (no Actions minutes needed for deploy).
  - GitHub Actions for: lint/typecheck/tests on PR, `prisma/drizzle migrate deploy` against the target Neon branch, and a scheduled keep-alive cron. Private-repo Actions = 2,000 free min/month — keep jobs lean.
  - Use **Neon GitHub integration** to auto-create/destroy a DB branch per PR and post the connection string.
- **Secrets / env management:**
  - Store secrets in **Cloudflare Pages/Workers environment variables** (per-environment: Preview vs Production) and **GitHub Actions Secrets** for CI.
  - Never commit `.env`; keep a committed `.env.example`. Secrets: `DATABASE_URL` (Neon, pooled connection for serverless), `R2_ACCESS_KEY_ID/SECRET`, `R2_BUCKET`, `CLERK_SECRET_KEY`/`AUTH_SECRET`, `RESEND_API_KEY`, `SENTRY_DSN`, `INSTAPAY_NUMBER`, `ADMIN_ALLOWLIST`.
  - Use a **Neon pooled (PgBouncer) URL** for the app and a **direct URL** for migrations.

### 4. Cost Ceiling & First Paid Upgrade Path

What breaks first as you scale, and the cheapest fix:

1. **R2 storage (10 GB) fills first** — user photos + payment screenshots. _Upgrade:_ R2 is pay-as-you-go beyond free: ~$0.015/GB-month storage, **still $0 egress**. 100 GB ≈ ~$1.50/month. Cheapest, most painless upgrade. Mitigate by compressing uploads and purging screenshots after order approval.
2. **Neon compute/storage** — at sustained traffic, 100 CU-hrs or 0.5 GB is exceeded. _Upgrade:_ Neon Launch ~$19/month (more storage, longer history, no scale-to-zero cold starts).
3. **Hosting** — if you stayed on Vercel Hobby, the **non-commercial clause forces Pro ($20/seat/month)** the moment you monetize; on Cloudflare you instead hit Workers 100k req/day → Workers Paid $5/month (10M req included). Cloudflare path is ~4× cheaper.
4. **Email (Resend 3k/month)** — hit when sending many link/approval mails. _Upgrade:_ Resend $20/month for 50k emails, or Brevo's higher free daily cap as a stopgap.
5. **Auth** — Clerk 10k MAU → Clerk Pro $25/month; or migrate to Auth.js on your own Neon DB for $0 (just engineering time).

**Realistic "first real bill" order:** R2 overage (~$1–2) → Resend ($20) → Neon Launch ($19) → Workers Paid ($5). You can run a paying MVP at **$0** and the first meaningful upgrade is typically **under $5/month**.

### 5. Backups, Image Optimization & Mobile/CDN Performance

- **Backups:**
  - Neon provides **point-in-time restore** via history retention (free tier ~24h window; longer on paid) — sufficient for early stage. Add a nightly **`pg_dump` via GitHub Actions** to an R2 `backups/` prefix for an independent copy (cheap insurance; R2 egress is free so restores cost nothing).
  - R2 objects: enable **versioning** and treat the bucket as the source of truth; payment screenshots are sensitive — keep them in a private bucket served only via signed URLs, and delete after approval per a retention policy.
- **Image optimization (critical for media-heavy links):**
  - Resize/compress on upload: convert recipient photos to **WebP/AVIF**, cap longest edge (~1600px), strip EXIF (privacy). Do it in a Worker or via Cloudflare Images variants so you store one optimized master.
  - Serve **responsive variants** (`srcset`) so a phone on a slow MENA mobile network pulls a ~50–150 KB image, not the original multi-MB upload.
  - Lazy-load step images; preload only the first 1–2 animation steps, prefetch the rest as the sequence plays.
- **Performance / CDN for mobile:**
  - All media goes through **Cloudflare's CDN with $0 egress and edge caching** — repeat opens of a viral link cost nothing and serve from a nearby PoP (Cloudflare has strong MENA presence).
  - Set long `Cache-Control` (immutable, content-hashed asset URLs) on images and animation assets; cache the rendered experience page at the edge where possible (it's read-mostly once created).
  - Keep animation/runtime JS small and bilingual-aware: ship **separate Arabic display fonts** (subset + `font-display: swap`), load only the locale's font, and set `dir="rtl"` per template variant to avoid layout shift.
  - For the unlock flow, the link page should be a fast static/edge-cached shell that fetches only a small JSON of step content + signed media URLs — so the first paint is instant even before media downloads.
